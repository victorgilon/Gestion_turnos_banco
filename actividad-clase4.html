🪜 2. REST o Eventos

Interacción REST Evento ¿Por qué?
1 X El registro envía los turnos al módulo de atención de manera asíncrona para que el flujo siga sin bloquear el sistema.
2 X La atención confirma al cierre de manera asíncrona, porque no necesita que la atención espere a que se procese el cierre.
3 X Las notificaciones a la pantalla y al administrador son asíncronas para que el sistema siga funcionando sin esperar confirmación.

🪜 3. Síncrono o Asíncrono

Interacción Síncrono Asíncrono Justificación
1 X El turno se envía sin detener el flujo del sistema.
2 X La confirmación de cierre no bloquea la atención.
3 X Las notificaciones no requieren respuesta inmediata.

Interacción 1

cliente

Como es comunicación por evento (asíncrona): El turno se crea igual, El sistema sigue funcionando, La notificación podría reintentarse automáticamente, No afecta la operación principal

Interacción 2

servicio de Turnos
Servicio de Usuario
ID del usuario, Solicitud de validación, Rol
Como es comunicación REST síncrona: No se puede crear el turno, Se devuelve error al cliente, La operación se detiene

Interacción 3

servicio de Turnos
Servicio de Reportes
Evento TurnoFinalizado, Tiempo de espera, Tiempo de atención Estado final
Como es asíncrono: El turno se finaliza igual, Los reportes pueden actualizarse después, Se puede reintentar el evento

🪜 2. REST o Eventos

Interacción REST Evento ¿Por qué?
Turnos -> Notificaciones NO SI Solo se informa que ocurrió algo (TurnoCreado, TurnoFinalizado). No necesita respuesta inmediata.
Turnos -> Usuario SI NO Necesita validar si el usuario está activo antes de crear el turno. Es una operación crítica.
Turnos -> Reportes NO SI Reportes solo reacciona cuando un turno cambia de estado. No bloquea el flujo principal.

🪜 3. Síncrono o Asíncrono

Interacción Síncrono Asíncrono Justificación
Turnos -> Notificaciones NO SI La notificación puede enviarse en segundo plano sin afectar la creación del turno.
Turnos -> Usuario SI NO Si no se valida el usuario, no se puede crear el turno. Debe responder inmediatamente.
Turnos -> Reportes NO SI Los reportes pueden actualizarse después sin impactar la operación en tiempo real.

🪜 6. Service Discovery

Con service discovery se deja abierto la comunicacion y se redirije a otro nodo
Con Service Discovery:Cada servicio se registra automáticamente cuando inicia. El sistema guarda su: Nombre lógico (ej: servicio-usuarios), IP actual, Puerto Estado (activo/inactivo)
En sistemas distribuidos es útil porque: Las IP pueden cambiar dinámicamente, Permite escalabilidad automática, Evita configuraciones manuales, Permite balanceo de carga, Aumenta tolerancia a fallos
En BEVS TurnoBank, lo aplicaríamos entre los servicios que se comunican por REST: Gestión de Turnos -> Usuario, Autenticación -> Usuario, Gestión de Turnos -> Sucursales
