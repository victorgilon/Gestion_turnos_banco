1. INTRODUCCIÓN

En el primer avance se realizó el análisis del problema y se propuso una arquitectura basada en microservicios para un sistema de gestión de turnos. En este segundo avance se presenta el avance funcional del sistema, evidenciando la implementación real de los servicios y la comunicación entre ellos dentro de un entorno distribuido.

2. DESCRIPCIÓN DEL AVANCE

2.1 Evolución del Sistema

En el primer corte se planteó una arquitectura teórica basada en microservicios, contemplando componentes como autenticación, gestión de turnos, sucursales y notificaciones. Además, se definió el uso de comunicación síncrona mediante servicios REST y la posibilidad de incorporar comunicación asíncrona basada en eventos.

Para el segundo corte, se inició la implementación de esta arquitectura en un entorno real utilizando contenedores Docker. Se añadió el servicio de notificaciones (notification-service), el cual ya se encuentra en ejecución; sin embargo, actualmente no realiza funciones activas.

Por otro lado, el bróker de eventos RabbitMQ se encuentra en proceso de implementación, por lo que aún no está configurado ni integrado en el sistema. Debido a esto, la comunicación asíncrona entre los microservicios todavía no ha sido puesta en funcionamiento.

2.2 Partes del Sistema Implementadas

Actualmente el sistema cuenta con una implementación parcial de una arquitectura basada en microservicios, en la cual se han desarrollado los siguientes componentes:

  • API Gateway como punto de entrada al sistema
  • Auth-Service para la autenticación de usuarios
  • Turno-Service para la gestión de turnos
  • Sucursal-Service para la administración de sucursales
  • Notification-Service agregado y en ejecución (sin procesamiento de eventos por el momento)

2.3 Funcionalidades Operativas

El sistema actualmente cuenta con funcionalidades básicas que permiten la gestión de usuarios, turnos y sucursales. Estas funcionalidades evidencian un avance en la integración de algunos servicios y el funcionamiento inicial del sistema BEVS en un entorno distribuido.

Actualmente, el sistema permite:

  • El registro de usuarios
  • El inicio de sesión (autenticación)
  • La creación de turnos
  • La creación y gestión de sucursales

2.4 Componentes No Implementados

Aunque el sistema cuenta con funcionalidades operativas, aún existen componentes en desarrollo o pendientes de implementación. Estos elementos son importantes para mejorar la experiencia del usuario y fortalecer la robustez del sistema.

Actualmente, se encuentran pendientes:

  • La implementación del envío de notificaciones (como correos electrónicos), ya que por el momento la información solo se almacena en la base de datos. Este proceso estará ligado a la futura comunicación entre servicios basada en eventos.
  • La integración completa del frontend con todos los servicios disponibles.
  • La validación de datos entre servicios, por ejemplo, verificar que la sucursal exista al momento de crear un turno.

3.2 Relación entre Servicios

El sistema funciona mediante una arquitectura de microservicios, donde cada componente cumple una función específica y se comunica con los demás a través de mecanismos principalmente síncronos.

Este enfoque permite un bajo acoplamiento entre los servicios, ya que cada uno gestiona su propia lógica de negocio.

El flujo general del sistema para la creación de un turno es el siguiente:

  • El cliente envía una solicitud al API Gateway
  • El API Gateway redirige la petición al microservicio correspondiente
  • El Turno-Service recibe la solicitud y ejecuta un middleware de verificación para validar el acceso del usuario mediante token
  • Una vez validado, el Turno-Service procesa la lógica de negocio para la creación del turno
  • Finalmente, la información del turno es almacenada en la base de datos

3.3 Cambios Respecto al Primer Avance

En el primer avance se había propuesto el uso de Service Discovery para la comunicación entre los microservicios. Sin embargo, en la implementación actual este componente no se incluyó.

En su lugar, se utilizó Docker, ya que permite gestionar los servicios en contenedores y facilita su ejecución en un mismo entorno.

Además, Docker permite que los contenedores se comuniquen entre sí mediante el uso de nombres dentro de la misma red, lo que hizo innecesario agregar una herramienta adicional para el descubrimiento de servicios.

4. COMUNICACIÓN ENTRE SERVICIOS

4.1 Tipo de Comunicación

El sistema utiliza comunicación síncrona mediante servicios REST para el intercambio de información entre los microservicios.

Este tipo de comunicación se basa en solicitudes HTTP, donde un servicio envía una petición y espera una respuesta inmediata.

En el caso de la creación de turnos, el cliente envía una solicitud al API Gateway, el cual actúa como intermediario y redirige la petición al Turno-Service.

Durante este proceso, la información viaja a través de la red en formato JSON, permitiendo una comunicación clara y estructurada entre los componentes del sistema.

El Turno-Service recibe la solicitud, procesa la información y devuelve una respuesta que sigue el mismo flujo de regreso hasta el cliente.

4.2 Endpoints Utilizados

  • POST /api/turnos → Crear un nuevo turno (requiere autenticación)
  • GET /api/turnos → Obtener lista de turnos (requiere autenticación)
  • GET /api/turnos/:turnoId → Obtener turno por ID
  • PUT /api/turnos/:turnoId → Actualizar turno (requiere autenticación)
  • DELETE /api/turnos/:turnoId → Eliminar turno (requiere autenticación y rol administrador o moderador)

4.4 Decisiones Tomadas en la Implementación

  • Uso de arquitectura basada en microservicios
  • Uso de Docker para despliegue
  • Uso de Docker Compose
  • Uso de variables de entorno mediante archivos .env
  • Uso de API Gateway

4.5 Configuración del Entorno

El proyecto utiliza archivos .env gestionados por la librería dotenv. Esta estrategia permite desacoplar el código fuente de la configuración específica garantizando seguridad y flexibilidad.

Categoría Variables Propósito
Servidor PORT, JWT_SECRET Define puertos y clave para validación de tokens
Persistencia USER_DB, PASS_DB, SERVER_DB, DB_NAME Credenciales y conexión MongoDB Atlas

4.6 Gestión de Configuraciones

La gestión de configuraciones se realiza mediante variables de entorno para credenciales, puertos y conexiones externas sin incluirlos directamente en el código fuente.

  • Mayor seguridad
  • Portabilidad
  • Configuración independiente por microservicio
  • Escalabilidad y mantenibilidad

4.7 Cómo se Asegura la Portabilidad del Sistema

La portabilidad del sistema se asegura mediante Docker, variables de entorno y Docker Compose.

Estas tecnologías permiten ejecutar el sistema en distintos entornos sin modificar el código fuente, manteniendo consistencia y facilidad de despliegue.
